# Task #3: Improve — Anatomy of a Prompt

## 1. Objective

The objective of this task is to improve the relevance and completeness of the generated website by using a structured prompt with six components: Role, Task, Context, Constraints, Expected Output, and Acceptance Criteria.

## 2. Structured Prompt Used

**Role:**
Act as an experienced frontend web developer specializing in responsive tourism websites.

**Task:**
Create a simple, attractive, and interactive single-page tourism website called "LakbayMarinduque" that promotes tourist destinations and local culture in Marinduque, Philippines.

**Context:**
The website is intended for local and international visitors who want to discover Marinduque's attractions, natural scenery, and cultural traditions. Feature Poctoy White Beach, Mount Malindig, and the Moriones Festival. Use clear, welcoming English and a visual style inspired by the island's beaches, greenery, and local heritage.

**Constraints:**
- Use semantic HTML5, CSS3, and vanilla JavaScript.
- Do not use frontend frameworks, backend services, or build tools.
- Make the layout responsive on desktop, tablet, and mobile screens.
- Use accessible navigation, descriptive image alternative text, and readable color contrast.
- Implement a mobile navigation menu and working destination category filters.
- Ensure interactive controls work with mouse and keyboard.
- Keep code organized, readable, and appropriately commented.
- Do not invent tourism facts, contact details, prices, or opening hours.
- Do not overwrite existing Zero-Shot baseline files.
- Save the new version separately in `outputs/structured/`.

**Expected Output:**
Create the following files:
1. `outputs/structured/index.html`
2. `outputs/structured/style.css`
3. `outputs/structured/script.js`

Link the CSS and JavaScript correctly using relative paths. Provide complete code that can run in a browser.

**Acceptance Criteria:**
- The page promotes Marinduque tourism and local culture.
- All three files exist in the specified folder.
- HTML correctly loads CSS and JavaScript.
- The page is responsive on desktop and mobile without horizontal overflow.
- Navigation links lead to the correct sections.
- Destination filters show only the selected category, and the All filter restores all destinations.
- The mobile navigation opens and closes correctly.
- Controls are keyboard-accessible and appropriately labeled.
- The website runs without a frontend framework or backend.
- Any unverified features and limitations are clearly identified.

## 3. Actual Output

The structured version was created separately from the original Zero-Shot files.

Files created:
- HTML: `outputs/structured/index.html`
- CSS: `outputs/structured/style.css`
- JavaScript: `outputs/structured/script.js`

The website includes sections promoting Poctoy White Beach, Mount Malindig, and the Moriones Festival. It also includes navigation, destination category filters, and responsive styling.

The visual design was subsequently improved with a refreshed color palette, typography, navigation, spacing, and destination cards.

Static checks confirmed that:

Browser testing was completed. Record the specific features tested, such as navigation links, category filters, mobile navigation, and the responsive layout, according to the tests actually performed.

## 5. Comparison: Zero-Shot vs. Structured Prompting

**Difference 1 — Specificity:** The Zero-Shot prompt only asked for a simple tourism webpage. The structured prompt specified the target audience, featured destinations, and cultural focus.

**Difference 2 — Technical requirements:** The structured prompt explicitly required responsive design, accessible navigation, keyboard interaction, working destination filters, and separate output files.

**Difference 3 — Evaluation:** The Zero-Shot prompt did not include detailed acceptance criteria. The structured prompt provided clear criteria for checking the generated website.

## 6. Observations

The structured prompt provided clearer instructions about the website's content, design, functionality, and file organization. The generated website was opened and tested in a browser. Static checks also confirmed that the output files and local links were present.

The structured prompt made it easier to evaluate the result because the requirements and acceptance criteria were clearly stated.

## 7. Conclusion

Structured prompting improves the clarity and completeness of AI-generated output by defining the role, task, context, constraints, expected output, and acceptance criteria.

Compared with Zero-Shot prompting, the structured approach gave more specific instructions and measurable requirements. This made the LakbayMarinduque website easier to evaluate and improve.

# Task #4: Few-Shot and Role Assignment

## Experiment A: Few-Shot Prompting

### Objective
To explore how examples influence the format and consistency of AI-generated output.

### Prompt Used
Use my existing LakbayMarinduque project as context.

Create exactly four additional travel checklist items for visitors exploring Marinduque, Philippines. Follow the format of these examples.

Example 1:
Item: Bring a reusable water bottle
Category: Travel Essentials
Description: Bring drinking water to stay hydrated during your trip.

Example 2:
Item: Respect local customs
Category: Cultural Awareness
Description: Be considerate of local traditions and community practices.

Generate exactly four additional items using the same three fields: Item, Category, and Description.

Requirements:
- Keep the items relevant to tourism, travel preparation, and responsible cultural tourism.
- Use simple, clear English.
- Keep each description short and practical.
- Avoid inventing specific local rules, prices, schedules, or tourism facts.
- Render the four items as a checklist using semantic HTML and native checkbox inputs.
- Return the four items and a complete, standalone HTML snippet.
- Do not edit or overwrite existing project files.
- Keep the format consistent with the examples.
- If multiple versions are generated, identify the recommended version and explain why.

### Actual Copilot Response
Copilot generated exactly four additional items:

1. Pack sun protection — Travel Essentials.
2. Check travel updates before setting out — Travel Preparation.
3. Leave natural places as you found them — Responsible Tourism.
4. Ask before taking someone's photo — Cultural Awareness.

Copilot also generated a standalone HTML document containing a heading, an unordered list, native checkbox inputs, and associated labels.

**Selected output:** The generated standalone HTML snippet was selected because it follows the requested format, contains exactly four additional checklist items, and can be saved as an independent HTML file.

### Output File
`outputs/few-shot/checklist.html`

### Observation
The examples helped guide the structure of the generated content. Copilot maintained a consistent Item, Category, and Description format while producing four additional items relevant to travel preparation, responsible tourism, and cultural awareness.

The generated HTML includes native checkboxes and matching labels. The snippet has not been integrated into the main LakbayMarinduque website.

### Testing Status
The output was inspected in Copilot Chat. Browser testing of the saved HTML file should be recorded after it is opened and checked in a browser.

## Experiment B: Role Assignment

**Prompt:** Assigned Copilot the role of a frontend accessibility reviewer and asked it to inspect the existing HTML, CSS, and JavaScript without modifying files.

**Actual response:** Copilot identified destination links pointing to a general section and several very small text sizes. It also recommended verifying focus outlines, screen-reader announcements, contrast, and responsive behavior.

**Selected output:** The accessibility review saved in `outputs/role-assignment-review.md`.

**Observation:** Role assignment directed Copilot's attention toward accessibility, semantic HTML, keyboard navigation, text readability, and usability. It also distinguished source-code findings from issues requiring additional testing.

**Testing status:** Code review completed. Browser, screen-reader, and contrast testing remain to be done.

## Task #5: Analyze Structured Reasoning and Refinement

### Analysis Prompt
Asked Copilot to compare `outputs/structured/` against the original requirements, identify two priority issues, recommend a minimal correction, and provide a verification procedure.

### Actual Recommendations
1. The Poctoy White Beach and Mount Malindig “Learn more” links point to the general `#plan` section instead of destination-specific content.
2. The mobile `.filter-button` font size is set to 8px, which may make the category labels difficult to read.

Copilot recommended increasing the mobile filter-button font size to at least 12px as a low-risk first correction.

### Selected Correction
**File:** `outputs/structured/style.css`

**Change:** Increased the mobile `.filter-button` font size from 8px to 12px.

### Verification Procedure and Result

- **Viewport width:** 360px.
- **Filter label readability:** The filter labels were readable on the mobile viewport.
- **Clipping or horizontal overflow:** No visible clipping or unwanted horizontal overflow was observed.
- **Category filter behavior:** The category filters worked as expected and displayed the matching destinations.
- **“All Places” behavior:** Selecting “All Places” restored all destination cards.
- **Mobile menu and Escape-key behavior:** The mobile menu opened and closed as expected, and the Escape key closed the menu.

### Observation
Copilot identified that the mobile filter labels used a small font size and recommended increasing it from 8px to 12px. After applying the CSS adjustment, the page was checked at a 360px viewport width. The filter labels remained readable, and the tested navigation and filtering interactions worked as expected.

The correction was verified through browser testing. These results apply to the checks performed and do not establish that every accessibility issue has been resolved.

### Limitations

The initial review was based on code inspection. Browser testing was performed afterward to verify the selected CSS correction and the tested filtering and navigation interactions. The checks were limited to the tested viewport and interactions; comprehensive accessibility, screen-reader, and color-contrast testing was not performed.
